# Contributing to Kwendi

Thank you for your interest in Kwendi.

Kwendi is a proprietary software and cultural-educational project. Contributions are welcome only from people who have been explicitly authorized by the Kwendi rights holder(s).

The publication of this repository does not grant anyone permission to copy, modify, redistribute, or contribute to the project without authorization.

---

## 1. Before Contributing

Before making any contribution, please make sure that you have received explicit permission to contribute to Kwendi.

Currently authorized contributors are:

- **Maria Katchakile Carlos Baptista**
- **Alessandra Pinto**

Additional contributors or collaborators may be authorized in the future on a case-by-case basis.

If you would like to collaborate with Kwendi, please contact the project owner before opening a Pull Request.

---

## 2. Types of Contributions

Authorized collaborators may contribute in areas such as:

- Software development
- Bug fixes
- Performance improvements
- UI/UX improvements
- Accessibility
- Educational content
- Language-learning materials
- Cultural research
- Documentation
- Testing
- Translation
- Automation
- Infrastructure
- Other improvements approved by the project owner

Not every proposed contribution will necessarily be accepted.

---

## 3. Reporting a Bug

Before reporting a bug, please check whether the issue has already been reported.

A good bug report should include:

- A clear and descriptive title
- A description of the problem
- Steps to reproduce the problem
- Expected behavior
- Actual behavior
- Relevant error messages or logs
- The environment in which the problem occurred
- Screenshots or other useful evidence when applicable

Please avoid including passwords, private keys, API keys, personal information, or other sensitive data.

---

## 4. Feature Requests

Feature requests should clearly explain:

1. What the proposed feature is.
2. Why it would be useful.
3. What problem it would solve.
4. How it could improve the Kwendi experience.
5. Any relevant examples or references.

A feature request does not guarantee that the feature will be implemented.

The project owner may accept, modify, postpone, or reject a proposal depending on the project's goals and priorities.

---

## 5. Pull Requests

Authorized contributors should:

1. Create a separate branch for their work.
2. Keep changes focused on a specific issue or improvement.
3. Use clear and descriptive commit messages.
4. Test their changes before submitting a Pull Request.
5. Update documentation when necessary.
6. Explain what was changed and why.
7. Include screenshots or other relevant information when the change affects the user interface.
8. Avoid unrelated changes in the same Pull Request.

Pull Requests should be reasonably small and easy to review whenever possible.

---

## 6. Pull Request Description

A Pull Request should explain:

- What was changed.
- Why the change was necessary.
- How the change was tested.
- Any known limitations or remaining issues.
- Any relevant issue or discussion.

Example:

```text
## What changed

Added offline progress persistence for learning modules.

## Why

Users should be able to continue their learning progress without an internet connection.

## Testing

Tested module completion, application restart, and data persistence on Android.
```

---

## 7. Code Quality

Contributors should aim to keep the code:

- Clear
- Maintainable
- Consistent with the existing project
- Well-structured
- Properly tested where applicable
- Free from unnecessary complexity

Avoid introducing dependencies unless they are necessary and compatible with the project.

---

## 8. Educational and Cultural Content

Kwendi contains educational and cultural material.

Contributors working on this type of content should take particular care with:

- Accuracy
- Context
- Respect for Angolan culture
- Language accuracy
- Appropriate attribution
- Reliable sources
- Avoiding unsupported claims

Do not submit content copied from third-party sources without permission.

When external sources are used, provide appropriate attribution and references where applicable.

---

## 9. Intellectual Property

Contributing to Kwendi does not automatically transfer ownership of the entire project to a contributor.

Contributors must have the necessary rights to submit any material they contribute.

Do not submit:

- Copyrighted material without permission
- Proprietary code belonging to another company or project
- Private or confidential information
- Personal data
- Content that violates another person's intellectual-property rights

Additional written agreements may be required for certain contributions or collaborations.

---

## 10. Confidential Information

Do not publish confidential information in:

- Issues
- Pull Requests
- Commit messages
- Source code
- Documentation
- Screenshots
- Discussions

This includes passwords, API keys, private credentials, private user data, internal communications, and other sensitive information.

If you accidentally expose a secret, notify the project owner immediately.

---

## 11. AI-Assisted Contributions

AI-assisted development may be used by authorized contributors when appropriate.

However, contributors remain responsible for reviewing and understanding the code or content they submit.

AI-generated material must not knowingly introduce:

- Copyright infringement
- Malicious code
- Security vulnerabilities
- Confidential information
- Unlicensed third-party material
- Incorrect educational or cultural information

Contributors should review AI-generated code before submitting it.

---

## 12. Community Behavior

All contributors and collaborators are expected to communicate respectfully and professionally.

The Kwendi project does not tolerate:

- Harassment
- Discrimination
- Threats
- Personal attacks
- Intimidation
- Deliberate disruption
- Malicious behavior
- Unwanted disclosure of private information

Technical disagreements are welcome.

Personal attacks are not.

---

## 13. Review Process

All contributions are subject to review.

The project owner may:

- Request changes
- Ask for clarification
- Modify a proposed implementation
- Reject a contribution
- Merge a contribution
- Postpone a contribution for future consideration

Submitting a Pull Request does not guarantee acceptance.

---

## 14. Authorization and Access

Access to private repositories, development environments, APIs, databases, credentials, internal documentation, or other project resources may be granted separately.

Authorization may be limited to the resources necessary for a specific collaboration.

Access must not be shared with other people.

---

## 15. Becoming a Collaborator

Kwendi may accept new collaborators in the future.

Potential collaborators may be evaluated based on:

- Technical skills
- Relevant experience
- Reliability
- Communication
- Respect for the project's goals
- Understanding of the project's licensing and intellectual-property requirements

Any additional permissions will be granted separately and may require a written agreement.

---

## 16. Questions and Contact

If you are interested in contributing or collaborating with Kwendi, please contact the project owner before submitting code or other substantial material.

For issues that contain sensitive security information, do not disclose the details publicly. Contact the project owner privately instead.

---

## 17. Final Note

Kwendi is being developed as a long-term software, educational, and cultural project.

Contributions should help improve the project while respecting its ownership, purpose, community, and cultural context.

Thank you for respecting the project and for your interest in Kwendi.
